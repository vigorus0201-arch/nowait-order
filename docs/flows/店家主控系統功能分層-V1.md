# 店家主控系統功能分層 V1

> 狀態：混合文件（現況 + 設計藍圖）｜版本：V1｜建立於 2026-04-03｜最後更新：2026-04-03
>
> 現況已實作的模組：Dashboard、POS、Orders、KDS、Menu

## 1. 文件目的

定義 NoWait Order 店家端各功能模組的邊界、路由、職責，以及模組之間的資料流與操作關係。

本文件回答三個問題：
1. 每個模組**負責什麼**、**不負責什麼**
2. 模組之間**如何連動**
3. 目前**哪些已落地**、哪些**待整合**

---

## 2. 系統拓撲

系統依使用者角色分為三層，共用同一個 `storeSlug` 與 `orders` 表：

```
─────────────────────────────────────────────
顧客層（Customer Layer）
─────────────────────────────────────────────
  /s/[storeSlug]              點餐頁（無 auth）
  /checkout                   結帳頁（無 auth）
  /order/success              確認頁（無 auth）
  /tracking/[storeSlug]       進度表（無 auth，待整合）

─────────────────────────────────────────────
店家操作層（Owner Layer）
─────────────────────────────────────────────
  /owner/[storeSlug]          Dashboard
  /owner/[storeSlug]/pos      POS
  /owner/[storeSlug]/orders   Orders
  /owner/[storeSlug]/menu     Menu
  ── 共用 layout，client-side auth guard（localStorage）

─────────────────────────────────────────────
廚房層（Kitchen Layer）
─────────────────────────────────────────────
  /kitchen/[slug]             KDS（廚房顯示系統）
  ── 獨立路由，無 owner auth，Supabase Realtime
```

**各層邊界說明：**
- 顧客層只能 **寫入** 訂單（orders insert）與 **讀取** 進度；不能修改狀態
- 店家操作層（Owner Layer）負責 **管理**；POS 只建立訂單，Orders 為備援操作端
- 廚房層（Kitchen Layer）為 **status 主要控制端**；即時推進訂單狀態

## 3. 各模組職責定義

---

### 3.1 Dashboard（營運總覽）✅ 已實作

> **【唯一責任】** 今日營運數據的唯讀彙總與 QR Code 產生。
> 只負責「讀取並呈現」；不介入任何訂單操作。

- **路由**：`/owner/[storeSlug]`
- **職責**：
  - 今日訂單數量與金額統計（總訂單、已完成、進行中）
  - 今日品項銷售排行（依數量排序）
  - 產生兩種 QR Code（一般遠端 / 到店掃碼）
  - Pending alert banner（有待處理訂單時警示並導向 Orders）
- **資料來源**：`orders` 表，`stores` 表（取店名）
- **更新方式**：手動 refresh 按鈕，無自動輪詢
- **不能做的事**：
  - 不能直接修改訂單狀態
  - 不顯示即時新訂單（需手動刷新）

---

### 3.2 POS（代客點單）✅ 已實作

> **【唯一責任】** 店員代客建立新訂單（orders insert）。
> 只負責「建立 pending 訂單」；不讀取既有訂單，不修改訂單狀態。
> **不可跨模組操作**：POS 不能取消或修改已送出的訂單，需切換至 Orders 頁。

- **路由**：`/owner/[storeSlug]/pos`
- **職責**：
  - 店員代替顧客完成點餐
  - mode 切換（內用：填桌號 / 外帶：填顧客姓名）
  - 直接送出 `pending` 訂單至 orders 表
- **資料來源**：`menu` 表（與顧客端相同來源）
- **寫入目標**：`orders` 表，`source: 'pos'`
- **不能做的事**：
  - 不能查看或修改已有訂單
  - 不能修改菜單
  - 送出後不能撤銷（需到 Orders 頁取消）

---

### 3.3 Orders（訂單管理）✅ 已實作

> **【唯一責任】** 後台訂單全覽與備援操作（狀態修改、取消）。
> 只負責「管理人員的操作介面」；非即時系統（polling 30s），不取代 KDS 廚房操作。
> **不可跨模組操作**：Orders 不能新增訂單（需到 POS），不能管理菜單（需到 Menu）。
> **status 控制權說明**：Orders 技術上可改 status，但應視為備援操作端，正常流程由 KDS 主導。

- **路由**：`/owner/[storeSlug]/orders`
- **職責**：
  - 顯示所有訂單（全狀態），依建立時間降序排列
  - 按狀態過濾（全部 / pending / preparing / completed / cancelled）
  - 手動推進狀態：`pending → preparing → completed`
  - 手動取消訂單（pending / preparing 狀態可取消）
  - 訂單詳情：品項、備註、顧客資訊、金額
- **更新方式**：初次載入 + `setInterval(30s)` polling，非 Realtime
- **桌機 / 手機差異**：
  - 桌機：左側清單 + 右側詳情面板
  - 手機：全螢幕 overlay 顯示詳情
- **與 KDS 的關係**：雙軌並行，兩端均可改狀態，以最後寫入者為準，不互斥

---

### 3.4 Menu（菜單管理）✅ 已實作

> **【唯一責任】** 菜單資料的 CRUD 與上下架管理。
> 只負責「menu 表與 categories 表的維護」；不操作訂單，不介入任何 status 流程。
> **不可跨模組操作**：Menu 不能查看訂單，不能改 orders 任何欄位。

- **路由**：`/owner/[storeSlug]/menu`
- **職責**：
  - 新增 / 編輯 / 刪除品項
  - 設定品項分類、排序、價格
  - 切換品項上架 / 下架（`available` 欄位）
  - 分類管理（categories 表）
- **影響範圍**：
  - 顧客端 `/s/[storeSlug]` 即時反映 `available` 狀態
  - POS 菜單與顧客端讀取同一份資料
  - KDS 顯示的是訂單快照（`items_json`），不受菜單修改影響

---

### 3.5 KDS（廚房顯示系統）✅ 已實作

- **路由**：`/kitchen/[slug]`（獨立，非 owner 路由底下）
- **職責**：
  - 即時顯示所有進行中訂單（pending / preparing / completed）
  - 新單入場音效提醒（Web Audio API，三聲）
  - 按鈕推進狀態：`pending → preparing → completed`
  - 清除已完成訂單（單筆或批次）
  - URGENT 標示（超過 10 分鐘未處理）
  - 按狀態過濾顯示
- **更新方式**：Supabase Realtime `postgres_changes`，即時推送
- **Auth 保護**：無。設計假設廚房為內網環境；若需保護可加 middleware
- **store_slug 過濾**：`/kitchen/[slug]` 只顯示該店；`/kitchen`（無 slug）顯示所有店
- **與 Orders 的關係**：同樣可改 status，雙軌並行，不互斥

---

### 3.6 顧客進度表（tracking）⚠️ 核心邏輯已驗證，待正式化整合

- **設計路由**：`/tracking/[storeSlug]`（待確認）
- **職責**：
  - 顧客查看整體叫號進度（非單一訂單詳情）
  - 顯示目前 `queue_number`（D001 / P001）排隊狀態
  - 內用 / 外帶進度分流顯示
  - 即時反映 KDS 的狀態更新
- **資料來源**：`orders` 表（`status`、`bring_number`）
- **更新方式**：目前原型為 polling（每 3 秒），可升級為 Realtime
- **Auth 保護**：無，顧客端匿名存取
- **目前缺口**：
  - `bring_number` 寫入邏輯尚未加入 checkout / POS
  - success page 尚未加入「查看進度」入口
  - tracking page 尚未正式整合進主流程
- **參考文件**：[顧客進度表與叫號系統-V1.md](./顧客進度表與叫號系統-V1.md)

## 5. 模組邊界釐清

| 問題 | 答案 |
|------|------|
| Orders 與 KDS 會衝突嗎？ | 不會。兩者都能改 status，以最後寫入 Supabase 者為準。實務上 KDS 為主要操作端，Orders 為備援。 |
| POS 單會進 KDS 嗎？ | 會。`source: 'pos'` 的訂單同樣是 `pending`，KDS 照常顯示，無特殊過濾。 |
| Dashboard 包含 KDS 嗎？ | 不包含。KDS 是完全獨立的路由與系統，Dashboard 只做今日統計，兩者無共用 layout 或 auth。 |
| 菜單下架後 KDS 有影響嗎？ | 沒有。KDS 顯示的是訂單成立時的 `items_json` 快照，不依賴 menu 表即時狀態。 |
| 顧客進度表是 Owner 後台的一部分嗎？ | 不是。設計為顧客端頁面，無 auth，路由獨立。與 KDS 共用 orders 表資料，但呈現方向不同。 |
