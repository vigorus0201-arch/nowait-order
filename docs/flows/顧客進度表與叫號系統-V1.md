## 一、文件目的

本文件定義 NoWait Order 中「顧客進度表與叫號系統（Queue System）」的核心邏輯。

此系統為產品核心體驗，負責：

* 顧客查看訂單進度
* 店家進行叫號操作
* 同步內用 / 外帶排隊狀態
* 建立「現場營運透明化」機制

---

## 二、核心概念

### 2.1 顧客不是看訂單，而是看叫號

```text
orders → KDS → queue → 顧客
```

顧客下單後，不是查看「單一訂單詳情」，
而是查看「整體叫號進度」。

---

### 2.2 queue 是系統，不是欄位

queue system 包含：

* orders（資料來源）
* queue_number（叫號）
* KDS（店家操作）
* tracking（顧客查看）
* progress（顯示層）
- 組成：queue_number + status + KDS + tracking
---

## 三、關鍵術語定義

### 3.1 queue_number（叫號）

```text
D001 / P001
```

* D = 內用（Dine-in）
* P = 外帶（Pickup）

用途：

* 顧客查看叫號
* 店家叫號
* 現場顯示

👉 與 order_code 不同（不可混用）

---

### 3.2 status（系統狀態）

```text
pending → preparing → completed → cancelled
```
> 注意：KDS 程式碼實際值為 `completed`。`success/page.tsx` interface 仍用 `done`，待統一。

用途：

* 系統內部流程
* KDS 操作依據

---

### 3.3 progress（顧客顯示）

progress 為 status 的 UI 映射：

| status    | 顧客顯示 |
| --------- | ---- |
| pending   | 等待中  |
| preparing | 製作中  |
| done      | 可取餐  |
| cancelled | 已取消  |

👉 progress 不為 DB 欄位

---

### 3.4 tracking（顧客進度頁）

用途：

* 顯示整體叫號進度
* 顧客查看排隊狀態
* 非單一訂單頁

---

## 九、正式化待辦清單（整合缺口）

以下為原型驗證後，進入正式流程前需要補齊的項目：

1. **status 值域統一**：`success/page.tsx` TypeScript interface 的 `done` 改為 `completed`（對齊 KDS 實際值）
2. **命名統一**：`bring_number` / `queueDisplayNo` 統一正式術語為 `queue_number`
3. **寫入邏輯**：`checkout/page.tsx` 補入 `queue_number` 寫入（D/P 格式，對應 source 欄位）
4. **主流程串接**：`success page` 加入「查看進度」入口，導向 tracking page
5. **tracking page 正式化**：移除原型假資料，改為讀取真實 stores + orders 資料

## 十一、設計原則

1. 顧客只需看 queue，不需理解系統
2. UI 必須極簡（現場可快速辨識）
3. 所有邏輯以 KDS 為中心
4. 不增加顧客操作負擔

---

## 十二、總結

NoWait Order 的核心不是訂單管理，

而是：

👉 **現場叫號系統（Queue System）**

顧客透過叫號了解進度
店家透過 KDS 控制節奏

兩者必須同步。
